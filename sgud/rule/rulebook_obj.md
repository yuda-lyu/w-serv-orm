## R-OBJ-01 使用端物件之迭代與複製: 只走自有可列舉鍵,不觸發原型 setter,自有 `__proto__` 鍵 fail-closed

- 狀態: 已套(1.1.11 之後,2026-10-17;裁示 D1、D2、D4;超出 D2 字面之存取器/不可讀 reject 與任何深度檢查,主控 2026-10-17 複審裁示採用(T3、T4);規則 5 深度上限與 R-ERR-01 規則 5 邊界保證為 run02 新增;規則 6 find 複本等價為 2026-10-19 第 33 項批 3 第 2 次執行新增,主控裁示修外審 sol F1;經 sol 與 Argon 共三輪外審修正; **2026-10-20 第 82 項(Argon 外審第三輪 A-07、B-02 之核實與修正)新增規則 5 續(find 之最長路徑深度與展開後容器數)與規則 7(寫入列與批次容器: id 讀取、頂層列乾淨判準、空洞),R-INPUT-01 規則 1、2 增批次容器檢查,R-MIX-01 增規則 6(mix.del 列之 id)**).來源: `建議w-serv-orm修正.md`(w-serv-webdata 主責 agent 2026-10-17 提出;審計 run01 經自建 lowdb 夾具重現屬實).
- 單一擁有者: `src/getMapOrm.mjs` mapOwn(使用端物件之複製與逐鍵轉換,唯一之迭代處)、getReasonBadKey(自有 `__proto__` 鍵、存取器屬性與不可讀之判定,唯一之檢查處)、getErrFind(find 之檢查)、getMsgsBadKey(寫入列之檢查與訊息)、MAX_DEPTH_FIND(find 之深度上限,規則 5).
- 規則:
  1. 使用端物件(find 條件、id 之條件物件、寫入列)之迭代一律以 `Object.keys` 走自有可列舉鍵,不得對其用 lodash `each`、`map` 等集合函數: lodash 對具非負整數 `length` 屬性之物件(如 `{length:1,name:'x'}`)採陣列樣迭代,只走索引 `0..length-1` 而不走自有鍵,真實鍵全數遺失.陣列(wsemi isarr 為真者)以索引迭代,不在此限.
     - 後果: select、delAll 之條件整個消失(select 回全表、delAll 刪全表);寫入列整列內容遺失且主鍵被改為產生值(insert、mix),或 save 單筆之列變 `{}` 而不寫入並回報 `{id: undefined}`.
     - `length` 為極大整數時迭代次數即其值,且複本上逐一建立同數量之屬性: 空 callback 實測 2e7 次 61 ms;castIdFind 路徑(find)與 wsemi clearXSS 路徑(巢狀欄位值)皆在複本建立 N 個屬性,實測 `length` 5e6 約增 163 MB(每屬性約 32 B),外審 opus 於 256 MB 堆積限制下 `length` 1e8 即 OOM 崩潰(exit 134),故可由資料通道之單一請求使整個行程崩潰.本規則關閉 find 與寫入列頂層之向量;欄位值內之巢狀物件由 wsemi 1.9.18 關閉(見已知限制).
  2. 複本之建立不得觸發原型 setter: 以 `Object.fromEntries`(mapOwn)或展開 `{...v}` 建立自有屬性,不用 `r[k] = v`(`k` 為 `__proto__` 時改設 `r` 之原型而不建立自有屬性,該鍵自此消失,ORM 所見之條件與呼叫端(含授權函數)所見者不同).
  3. fail-closed 檢查(getReasonBadKey): 檢查對象之任何深度(一般物件之值、陣列之元素)含下列者 reject,其餘型別(Date、Map、Set、函數等)不進入:
     - `proto`: 自有 `__proto__` 鍵,不論可否列舉,陣列本身亦檢查(自有鍵以 `Object.prototype.hasOwnProperty.call(v, '__proto__')` 判定,故物件字面量 `{ __proto__: x }`(設原型)不算).自有 `__proto__` 鍵可由 `JSON.parse`、`Object.fromEntries`、展開 `{...o}`、`structuredClone`、對 `Object.create(null)` 賦值產生(外審 opus 與審計實測),不限於 JSON.
     - `accessor`: 存取器屬性(getter、setter).理由: getter 每讀一次可能不同,令「檢查之值」不等於「使用之值」(外審 sol F1 實測: 以第一次讀回 `'a'`、第二次讀回 `'b'` 之 getter,字串型主鍵表之 select 改查 `b`、delAll 改刪 `b`,並可使檢查通過之 `__proto__` 於第二次讀出);getter 拋錯則繞過固定訊息並回顯其拋出之值(sol F4、opus #2b).檢查以屬性描述子讀值,不呼叫 getter.
     - `unreadable`: getReasonBadKey 檢查時拋錯(Proxy 之 ownKeys/描述子陷阱、find 之已撤銷 Proxy).列本身在更早之形狀檢查(`isobj` 讀 `Symbol.toStringTag`)即拋錯者(已撤銷之 Proxy 列、get 陷阱拋錯之列),由 R-ERR-01 規則 5 之邊界保證以 `failed to process input` reject.
     - **批次容器**: insert、save 之輸入陣列之各索引、mix 之 `add`/`del`/`diff` 屬性亦以屬性描述子檢查,存取器即 reject(`failed to insert data, unsupported accessor property: data[k]`;mix 容器為 `invalid input of mix, unsupported accessor property`),使其後之各次讀取為資料屬性之讀取而與檢查之值一致(外審 opus 二輪 F1: 容器為 getter 時,各檢查各自重讀,前幾次讀回乾淨列、其後讀回含 `__proto__` 之列).
     - 陣列之判定用 `Array.isArray`(不用 `isarr`): 偽造 `Symbol.toStringTag` 為 `Array` 之物件不當陣列走訪(否則其 `length` getter 被呼叫),亦不進入(與 Map、Set 同,屬「其餘型別」).
     - find(select、delAll): `invalid find of select, unsupported key[__proto__]`、`invalid find of select, unsupported accessor property`、`invalid find of select, unreadable value`,delAll 同.
     - 寫入列(insert、save、mix 之 add 與 diff): 整批 reject 且於任何寫入之前,依原因分組列位置: `failed to insert data, unsupported key[__proto__]: data[k]`、`failed to save data, unsupported accessor property: data[k]`、`failed to insert data, unreadable value: data[k]` 等;mix 之 add 為 insert 句、diff 為 `failed to update data, …`,多組以 `; ` 串接(同 R-INPUT-01 規則 2).
     - 訊息只列固定字句與位置,不回顯客戶端之值.
  4. 檢查之順序見 R-INPUT-01 規則 4: find 之檢查在 R-ID-02 轉型之前;寫入列之檢查在形狀檢查之後、R-ID-02 轉型之前.檢查本身以堆疊迭代並以 seen 防循環,不爆呼叫堆疊.
  5. find 之**巢狀深度上限**(MAX_DEPTH_FIND = 64): getErrFind 以容器層數(一般物件與陣列各算一層,根為第 1 層)計深度,走訪到第 65 層容器即 reject `invalid find of select, too deep`(delAll 同),不再走訪更深層.
     - 理由: castIdFind 以遞迴處理 `$and`/`$or`,遞迴深度即呼叫堆疊深度(2026-10-19 前另有 castIdFind 遞迴 `$nor`、castIdCond 遞迴 `$not`,因屬系列白名單外而移除,R-WL-01).實測(Node 24.19.0,2026-10-17,字串型主鍵表 select,替身 ORM,`tmp/audit/probe-depth.mjs` 二分,當時之碼)`$and` 巢狀約 1173 層(約 2346 個容器)、`$not` 鏈約 1857 層即 RangeError,以 Error 物件 reject(違反 R-ERR-01 規則 1);整數型主鍵表與無該表者原物件交 ORM,其後端自身之遞迴同受上限保護.實際爆堆疊之閾值隨呼叫時之堆疊用量而變,故取遠低於之值.
     - 取值: 64 個容器層 ≈ 32 層邏輯巢狀(`$and`/`$or` 每層 2 個容器),約為實測閾值之 1/36;遠大於合理查詢(庫內實際用到之條件最深為 `{id:{$in:[…]}}` 共 3 個容器,見 dspec 一之二;含 `$or` 內 `$and` 內等值之極端組合亦不過 7 個容器).
     - 寫入列不設深度上限(評估結果): getReasonBadKey 為堆疊迭代,本套件對列之處理皆單層(mapOwn、castIdRows 非遞迴);欄位值內之遞迴由 wsemi clearXSS(含 lodash cloneDeep)進行,約 1e3 層以內通過,1e4 層起拋 RangeError,被 adjustData 之 try/catch 轉為固定字串 `failed to adjust data`(實測 insert、save、mix.add、mix.diff 於 1e4 與 1e5 層皆如此,ORM 未被呼叫),無 Error 物件外洩.此結論依賴 wsemi 之遞迴與預設呼叫堆疊: 通過之層數隨 JIT 狀態浮動(外審 opus 二輪實測冷啟動約 1000 層通過、1500 層失敗,暖機後約 3000 層通過、4000 層起失敗),`node --stack-size=8000` 下 1e4 層亦通過而交給後端(服務端以 `--stack-size`/`NODE_OPTIONS` 加大堆疊者適用);故測試 T02 只斷言「不以 Error 物件 reject」,不鎖定 `failed to adjust data`.
  5 續. **find 之最長路徑深度與展開後容器數**(2026-10-20 第 82 項,Argon 外審第三輪 A-07;經 getReasonBadKey 之 strict 走訪全數通過後、品牌網之前,對根呼叫 `measureFind`):
     - 缺陷(修前): getReasonBadKey 以 `seen` 去重,深度只計**首次到達**之層數,共用子結構(DAG)可繞過 MAX_DEPTH_FIND(根之 `$or` 先把鏈上節點置於淺層,實測最長路徑 129、403、1003 個容器皆通過); castIdFind 依路徑展開而無去重亦無上限,指數型 DAG(`x_{i+1}={$and:[x_i,x_i]}`)k=20 約 1.1 秒、+213 MB,k=22 約 5.7 秒、+762 MB,`--max-old-space-size=256` 下 k=22 即 exit 134(無法 catch)——僅字串型主鍵表與型別未知者(經 castIdFind); 整數型主鍵表與無該表者原物件交後端,後端(wsemi cvOrmFind `maxNodes`=100000)自行擋下.僅直呼(行程內)可達: JSON 只能產生樹.
     - 規則: ①最長路徑超過 MAX_DEPTH_FIND(64 個容器)或有循環 → `too deep`(循環以前由 castIdFind 爆堆疊而被邊界保證轉為 `failed to process input`,現所有表型態皆 `too deep`); ②**展開後物件數**(不含陣列; 共用子結構依出現次數重複計)超過 MAX_NODES_FIND(100000,與 wsemi cvOrmFind 之 `maxNodes` 同值) → `too large`(訊息 `invalid find of <mode>, too large`).口徑: 後端 `spend()` 計節點(條件物件、運算子物件、純量各計 1,**`$and`/`$or` 之陣列不計**),本層只計物件,故為其子集——凡本層因 `too large` 拒收者後端必也拒收,本層不拒收後端會接受者(castIdFind 只經物件遞迴 `$and`、`$or` 之元素,陣列元素不展開,故不計陣列仍足以限制其展開量).**更正**: 本規則首版(及審計回應 §3.4)曾以「容器數(含陣列)」計並宣稱此性質,外審 minimax F2 以真 cvOrmFind 實測反例(每個條件物件帶 `$and`、`$or` 各一個單元素陣列之滿二元樹 d=15: 本層容器數 131,069 > 100,000 而後端節點數 98,303 接受)推翻,改為只計物件.深度仍以容器(物件與陣列各一層)計.
     - 演算法: 顯式堆疊之記憶化後序走訪,每個容器只展開一次(O(節點+邊));堆疊深度不超過 maxDepth+1(逾即返回);展開數以飽和方式累計(逾上限即返回,不產生大數); 狀態標記(走訪中)須在結果值域之外(實作用 `-1`;曾用 `1` 與「展開數為 1 之葉容器」碰撞而誤判循環,見經驗檔).首次到達深度檢查保留作為樹的早期退出.合理之重用(同一子條件於多處)不受影響.
     - 原型鏈長度: isCleanChain 逾 MAX_CHAIN(64)個物件(含自身,即鏈上至多 65 個)者視為不乾淨(外審 sol F08: 共用陣列帶 P 層原型而被引用 E 次時,measureFind 與 castIdFind 每次分類重掃原型鏈為 E x P; 合法物件之原型鏈至多數層,現每次分類成本有界).
     - 測試: S06(含鍵序 'q-first'、'p-first'、'tri' 三種,後者使兩個走訪都先經淺路徑展開共用鏈,只有 measureFind 之共用節點檢查或完成時檢查抓得到; 無共用樹 100,000/100,001 個物件; Date 葉之 64/65 容器邊界)、S07、S13(原型鏈長度)、A28(api-objcopy); C04 之預期更新.變異: 共用節點深度檢查與完成時檢查單獨移除各為等價(兩者量相同、互相涵蓋),同時移除(M25c)必須轉紅.最終程式全量變異(`tmp/run02/mut/run.mjs`,68 種 + 基準,對 unit-objcopy 與 api-objcopy 兩檔共 122 案,基準全綠): 64 轉紅、4 存活皆為等價或不可達——M25、M25b(上述單獨移除)、M14d(`getItemsNotObj` 之 isArr 還原為 isarr: 偽造 `Symbol.toStringTag` 之類陣列物件在更前面的 `getErrBatch` 以 `isCleanChain` 已整批拒收,該站收不到與 isArr 判準有別之輸入,不可達)、Y06(measureFind 堆疊頂深度檢查放寬一格: 多出之一格由其後的子節點入堆疊檢查或出堆疊時的 `stack.length + dep` 檢查補上,接受/拒收之集合不變,僅影響深度與展開數同時超限時回報 `too deep` 或 `too large` 哪一個,規格未訂其優先序,不為它加測試).
  6. **find 之複本須與原物件等價: 後端白名單所見者不得因本套件之複製而與呼叫端所給者不同,且檢查期間不得執行使用端程式**(2026-10-19 第 33 項批 3 第 2 次執行,外審 sol F1 與第二、三輪;僅 find,寫入列不適用,見已知限制).「等價」指複本等於呼叫端可見之自有資料(自有可列舉字串鍵之資料屬性與陣列索引);原型身分之正規化(跨 realm 之純物件與陣列、null 原型之陣列、陣列子類別)不算洩漏,不得發生者為: 複本洗掉隱藏資料(不可列舉鍵、Symbol 鍵、陣列額外屬性)、洗掉內部槽(內建品牌物件)、讀進繼承之資料(空洞陣列之原型索引、原型上之條件),或檢查途中執行使用端程式令條件被改動.
     - 根因: 字串型主鍵表之 castIdFind、castIdCond 以 mapOwn(只走自有可列舉字串鍵)與 lodash `map`(只走索引、以 `array[index]` 讀值)複製 find,而**檢查與複製各用一套型別判準**(檢查看 `Array.isArray`、`isobj`、自有鍵;複製看 `isobj`、`isarr`,即 `Object.prototype.toString` 之標籤),且判準的執行會**執行使用端程式**: 標籤可由自有鍵、原型或原型上之 getter 提供(讀標籤時 getter 被執行); `in` 運算子遇 Proxy 原型會執行 has 陷阱;`p.constructor` 可為 getter;走訪 Proxy 時其陷阱被執行——皆可在檢查途中改動已檢查之條件(外審第三輪 A-02~A-04),使「檢查之值」不等於「使用之值」.複本又洗掉不可列舉鍵、Symbol 鍵、陣列額外屬性、繼承之索引、原型身分與內建品牌物件之內部槽(Map、Set、TypedArray 等,含原型被改為 null 者),令白名單版後端(wsemi `cvOrmFind`)本會 reject 之條件變成較寬甚至無條件(實測 delAll 全刪).逐形狀補洞會持續漏(第一版被找出 4 類,第二版又被找出 4 類),故修法為結構性:
     - **①檢查與複製共用同一分類器 `getKindFind(o)`**: `typeof o !== 'object'`、`null`、`!isCleanChain(o)`、`isBrandObj(o)` 者回傳 null(不是容器: 原始值、函數、Date,及有 Proxy、有標籤、內建品牌物件者); `Array.isArray(o)` 為 'arr'; `isobj(o)` 為 'obj'; 其餘 null.castIdFind、castIdCond 只複製 'obj'、'arr',其餘原值或原參考交後端(不再用 `isobj`、`isarr` 直接判定).
     - **②檢查期間不執行使用端程式**: `isCleanChain(o)` 逐層走 `o` 及其原型鏈,以 `util.types.isProxy`(不觸發陷阱)與 `Object.prototype.hasOwnProperty.call(x, Symbol.toStringTag)`(只查自有屬性之有無,不讀值)判斷,有 Proxy(含原型鏈上者)或任何自有標籤即不乾淨;不用 `in` 運算子、不呼叫 `isobj`/`isarr` 於未確認乾淨之節點.getErrFind 對根亦先以 `types.isProxy` 判斷(Proxy 含已撤銷者一律 `irregular`,不觸發任何陷阱).
     - **③檢查(getReasonBadKey 第 3 參數 `strict`,find 一律開啟,不論 isIdCast)對走訪到之每個物件型別值 fail-closed**:
       - 不乾淨(Proxy、標籤)或內建品牌物件(isBrandObj): `irregular`.
       - Date(`types.isDate`)為葉(原值交後端,後端只讀其時間槽),但須乾淨: 有任何自有屬性(含 `__proto__` 鍵、getter、不可列舉者)→ `irregular`(外審 A-06).
       - 物件節點: 須為純物件(isPlainObj)否則 `irregular`;`Reflect.ownKeys(o).length === Object.keys(o).length`(無 Symbol 鍵、無不可列舉鍵)否則 `hidden`.頂層之非純物件由 getErrFind 先以 `need an object` 回絕.
       - 陣列節點: 每個索引 0..length-1 須為自有可列舉資料屬性(**空洞 → `irregular`**、不可列舉元素 → `irregular`、存取器 → `accessor`),且 `Reflect.ownKeys(a).length === length + 1`(只有索引與 `length`,無額外屬性,含 Symbol 鍵與不可列舉者)否則 `irregular`.空洞不再放行(第一版維持 P05 照常交 ORM): 外審第二輪 A-02 以繼承索引之空洞陣列(`Object.setPrototypeOf(new Array(1), {0:'a1'})`)實測,檢查跳過空洞而 `map` 以 `array[index]` 讀到繼承值.全為自有索引則 `array[index]` 無繼承讀取.
